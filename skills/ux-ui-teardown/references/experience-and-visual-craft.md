# Experience and visual craft

## UI craft is not the same as taste

Treat these as inspectable craft dimensions:

- hierarchy and focal order;
- color-system coherence;
- typography scale, rhythm, measure, and contrast;
- spacing rhythm and container logic;
- alignment and composition;
- responsive re-composition;
- component-family consistency;
- imagery and crop quality;
- density and whitespace balance;
- visual feedback/state clarity;
- motion and transition quality;
- perceived responsiveness and visual stability;
- intentional asymmetry versus accidental imbalance;
- generic/template-like presentation versus project-specific design choices.

Taste is narrower: personal preference among multiple coherent solutions.

## Audience fit

Evaluate authenticity and appropriateness relative to audience and scale.

Possible useful axes:

- intentional <-> accidental
- specific <-> generic
- human <-> sterile
- coherent <-> patched together
- confident <-> trying too hard
- engaging <-> merely transactional
- appropriately scoped <-> overproduced/underdeveloped

Do not assume "expensive-looking" is always better. Basic, restrained, or even rough visual language can be excellent when it is deliberate and right for the product.

For global or mixed audiences, include locale-sensitive craft only when relevant: text expansion/truncation, RTL resilience, date/number/currency formatting, local terminology, and whether global consistency has flattened necessary local specificity.

## Engagement quality

Use this model only to organize thinking:

```text
effort -> feedback -> progress -> payoff
```

A small decision can improve UX when it:

- changes what the user sees next;
- reduces irrelevant information later;
- clarifies the user's own needs;
- creates visible progress;
- improves the actual service/result rather than merely producing the feeling of personalization.

Reject interaction that exists only to manufacture engagement or collect unnecessary data.

Also distinguish engagement from coercion. More clicks, time-on-task, sign-ups, or conversions are not evidence of better UX when the interface obscures alternatives, pressures refusal, manufactures urgency, or makes reversal/cancellation harder than acceptance.

## Interaction and motion polish

Inspect the interface between static screenshots:

- hover, pressed, selected, focus, disabled, loading, success, and error feedback;
- transition timing and whether motion explains state change or merely decorates it;
- whether controls feel immediate or laggy;
- whether loading feedback preserves orientation and confidence;
- layout shift or delayed UI that makes the product feel unstable;
- repeated animation that slows work or distracts from the task;
- reduced-motion behavior when the product/context makes it material.

A polished static layout with weak interaction feedback is not polished UI.

## Perceived performance

Judge the user-visible experience, not only implementation speed.

When measurements are available, use relevant field/lab evidence for loading, interaction responsiveness, and visual stability rather than declaring a product fast or slow from one subjective run. Field behavior is stronger than a single lab run for real-user claims.

Performance engineering/root-cause analysis belongs elsewhere; this skill owns whether delay, jank, or layout instability harms momentum, comprehension, trust, or control.

## Visual-attention evidence

When real eye-tracking or credible predictive-attention tooling is available, use it as supporting evidence for first-impression hierarchy, CTA competition, and likely visual attention.

Do not treat attention prediction as proof that users understand, trust, prefer, or will act. It measures or predicts attention, not meaning.

## Visual anomaly pass

Deliberately search for:

- random spacing or width changes;
- weak/competing CTAs;
- awkward line wraps;
- mismatched radii/shadows/borders;
- dead space that feels accidental;
- cramped responsive states;
- inconsistent icon families;
- questionable crops or image scaling;
- palette decisions that technically pass contrast but visually fight;
- sections that look imported from another site;
- components that change design language without reason;
- layout that is technically responsive but visually loses hierarchy;
- copy/image combinations that read as stock, templated, or AI-generated without project specificity;
- interaction states whose visual language changes unexpectedly;
- motion/timing that feels delayed, twitchy, excessive, or unrelated to state change.

Explain why something looks off. Do not stop at "looks bad."
